# Security policy

INVENTORY is a single-user Windows desktop application. It keeps all of its data on the local computer and does
not use any server. This page explains which versions receive security fixes, how to report a vulnerability, what
the application protects against, and what it deliberately does not.

The detailed audit reports (in French) are in [`docs/audit-securite.md`](docs/audit-securite.md): the full audit of
version 1.0.0 and the review of version 1.8.2.

## Supported versions

Only the latest release receives security fixes. Please update before reporting an issue.

| Version | Supported |
| --- | --- |
| 1.8.2 (latest) | yes |
| earlier versions | no: install the latest release (your data is kept and migrated automatically, after a backup) |

## Reporting a vulnerability

Please **do not open a public issue** for a security problem.

Use GitHub's private vulnerability reporting instead: open the **Security** tab of this repository, then
**Report a vulnerability**. The report is visible only to the maintainers.

Please include:

- the version of INVENTORY ("Paramètres" page, "Informations système" section) and of Windows;
- what an attacker needs (a file to import, a database or data folder to open, another program on the computer…);
- the steps to reproduce, and if possible a minimal file or database that triggers the problem
  (never send real personal data: use made-up names).

The report is handled privately until a fixed release is available. The advisory is then published, crediting the
reporter unless you prefer to stay anonymous.

## Threat model

INVENTORY makes no network connection and has no remote interface, so a remote attacker is out of scope. The
realistic attackers considered are:

1. **a malicious file** that the user imports into a folder (a document, an image, a disguised script…);
2. **malicious data**: a database (`donnees.sqlite`) or a whole data folder received from someone else;
3. **hostile script** that would run inside the application window (through 1 or 2) and call the application's
   back-end commands;
4. **another program or another Windows account** on the same computer.

## What the application guarantees

These statements describe the code of the current release. Each one is checked by an automated test (Rust unit
tests, the end-to-end suite that drives the released executable, or the release build checks), except the two marked
"(code review)", which were verified by reading the code.

**Local only**
- The application sends no network request (code review; the end-to-end suite also fails on any request to anything
  other than the application itself). All data stays in `%APPDATA%\fr.entitesdossiers.app` (database,
  imported files, backups, error log).
- The window can only show the application itself: navigation to other addresses, new windows and downloads are
  refused, and every outgoing HTTP, WebSocket or FTP request from the window is answered locally with an error
  before it leaves the computer.

**Imported files**
- The type of a file is decided from its content (signature bytes), never from its name. A preview is shown only for
  a real PDF or a real image; an HTML page or an SVG renamed `.pdf` or `.png` is never rendered.
- Only common document types (PDF, images, text, office documents, e-mails) can be opened with the default Windows
  application. Any other file is stored with a neutral `.bin` extension and can only be saved elsewhere.
- Imported copies, and copies saved elsewhere, carry the Windows "downloaded from the Internet" mark
  (`Zone.Identifier`, zone 3), so that Office opens them in Protected View with macros blocked.
- File pickers are opened by the back end: the interface never supplies a file path. Imports are limited to 200 MB.
- A stored file name read from the database must be a random identifier generated by the application: a path, a
  `..`, a network path, an alternate data stream or a link is refused, so no deletion or opening can reach a file
  outside the application's `fichiers` folder.

**Database**
- An existing database is checked read-only before it is opened: known version, integrity check, exact expected
  structure (no unknown table, no trigger, no view), valid references, consistent folder tree. A refused database is
  left untouched and the user is told where it is and what to do.
- All SQL queries are parameterised (code review). Oversized or unreadable content is bounded when written and when displayed, and
  never prevents the rest of the data from opening.
- SQLite runs in defensive mode with an untrusted schema; deleted data is overwritten (`secure_delete`).

**Interface**
- Strict Content Security Policy: scripts and styles only from the application itself (`script-src 'self'`,
  `style-src 'self'`, no inline script or style), no plug-in objects, no external frames.
- The interface is granted only the window permissions it uses; opening files, choosing files and reading the
  disk are done by the back end only.
- Text coming from the data is always displayed as text, never interpreted as HTML.
- Error messages shown to the user never contain file paths, SQL or internal details; those go to
  `journal-erreurs.log` in the data folder.

**Your data**
- A backup is made automatically before every reset ("Effacer toutes les données" or reloading the sample data) and before every database migration, in the
  `sauvegardes` folder. The three most recent reset backups are kept, and no backup younger than seven days is
  deleted; migration backups are never deleted.
- Imported files are never deleted at start-up, even if the database no longer references them.

**Build**
- Release builds are compiled with locked dependencies, Control Flow Guard, ASLR, DEP, CET shadow-stack
  compatibility, overflow checks and no machine-specific paths; the build refuses to produce an installer if one of
  these checks fails.

## Known limitations

- **The installer is not code-signed.** Windows SmartScreen shows a warning, and nothing technically proves where
  the file comes from. Always check the SHA-256 checksum published next to the installer (see below).
- **Data is not encrypted.** It is protected by the permissions of your Windows profile only. Use BitLocker (or
  another full-disk encryption) to protect it if the computer is lost or stolen.
- **A malicious program already running under your Windows account** can read and change your data, and can make
  the application use another data folder (the `ENTITES_DOSSIERS_DONNEES` environment variable, used by the test
  suite). No application can protect against that.
- **Previews:** PDF previews are displayed by the WebView2 PDF viewer. A crafted PDF link could lead the preview
  area to another stored file; that file is never given access to the application's commands.
- **WebView2 speculative connections:** if hostile script ever ran in the window and tried to navigate away, WebView2
  may open a TCP connection to the target host before the application's filter applies; no HTTP request is sent.
- **Office macros:** office documents are allowed and may contain macros. They are marked as downloaded from the
  Internet so that Office blocks macros by default; do not unblock files you do not trust.
- **Installation folder:** keep the proposed installation folder (inside your user profile). Installing into a
  pre-existing shared folder keeps that folder's permissions.

## Verifying the installer

Each release provides `INVENTORY_<version>_x64-setup.exe` and `INVENTORY_<version>_x64-setup.exe.sha256`.
In PowerShell, in the download folder:

```powershell
Get-FileHash -Algorithm SHA256 -LiteralPath ".\INVENTORY_1.8.2_x64-setup.exe"
Get-Content ".\INVENTORY_1.8.2_x64-setup.exe.sha256"
```

The two hexadecimal values must be identical. If they differ, do not run the installer.

You can also build the installer yourself from the sources (`npm ci`, then `npm run livrer`; see the README).
